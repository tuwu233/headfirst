# 第5章｜单件模式：唯一实例，也要管好共享状态

[章节测验](练习题.html) · [Markdown 题稿](练习题.md)

> 学习目标：分清“一个访问入口”“一个实例”“线程安全”三个概念；会写受控的 Python 单例，也知道什么时候只创建一个普通对象更合适。

建议用时：速读 10 分钟，运行与练习 10 分钟。重点阅读第 3、5、6 节，不要只背双重检查锁。

## 1. 先记住这一句话

**单件模式，也常叫单例模式：控制某个类的实例数量，并提供获取该实例的统一入口。**

书中的巧克力锅炉只有一个物理设备。如果创建两个控制器，各自维护一份“是否空锅”的状态，就可能出现一个已经加料、另一个还认为可以继续加料的问题。

模式的动机是保持资源管理与状态的一致性，不是因为“全局访问很方便”。线程池、配置服务可能适合共享，但“适合共享”不自动等于“必须禁止创建第二个实例”。

## 2. 全局变量、单例、只创建一次，有什么区别

| 形式 | 能方便共享吗 | 能否阻止其他地方再构造一个对象 |
| --- | --- | --- |
| 模块里保存 `service = Service()` | 能 | 不能，仍可调用 Service() |
| 程序入口只创建一次，再传给使用者 | 能，依赖显式可见 | 靠组装约定，不强制禁止 |
| 类控制正常构造路径，重复构造返回同一对象 | 能 | 在约定的使用范围内能 |

Python 模块的顶层代码通常在首次导入时执行，之后同一进程中以同一模块名导入会复用缓存。因此模块级共享对象往往已经够用，但它不等于严格的“类只有一个实例”。

模块被重新加载、用不同模块名重复加载，或者程序启动多个进程时，都不能照搬“永远只有一份”的结论。

## 3. 书中多线程失败的原因：检查和创建是两个动作

不安全的懒初始化逻辑大致是：

```text
如果 instance 为空：
    instance = 创建对象
返回 instance
```

一次可能的交错：

| 步骤 | 线程 A | 线程 B |
| --- | --- | --- |
| 1 | 检查：为空 | 等待 |
| 2 | 暂停 | 检查：也为空 |
| 3 | 创建对象 A，取得它 | 暂停 |
| 4 | 已持有对象 A | 创建对象 B，取得它 |

两个线程可能各拿一份控制器。把变量声明为全局，或者用一个 `if` 包起来，都不能自动让“检查—创建—赋值”成为不可分割的操作。

Python 也不要靠 GIL 推导这段复合操作一定安全。共享状态应使用明确的同步机制；一次测试没碰到竞争，不等于证明没有竞争。

## 4. 把书中的 Java 方案翻译成 Python 决策

| 方案 | 关键点 | 学习与使用建议 |
| --- | --- | --- |
| 同步获取入口 | 检查与创建都在同一把锁内 | 简单清楚，本章 Python 示例采用这一方案 |
| 急切创建 | Java 在类初始化时创建静态实例 | Python 可在程序启动或模块首次执行时创建共享对象；两种语言机制不完全相同 |
| 双重检查加锁 DCL | 锁外查一次，锁内再查一次 | Java 正确版本需要 volatile 等内存模型保证；不要机械搬到 Python |
| Java 枚举单例 | 利用 Java 枚举的实例及序列化规则 | 这是 Java 的语言方案，不等于 Python Enum 可直接代替所有共享服务 |
| 模块级对象 / 显式传入 | 利用正常对象与程序组装 | Python 项目常见且更容易测试；先检查是否已经满足需求 |

Java 双重检查锁的第二次检查，是防止等待锁期间其他线程已经创建好对象；`volatile` 用来保证相关的可见性与安全发布，不能因为“我已经加了锁”就删除。已初始化后的访问通常走锁外路径；竞争初始化时，多个线程仍可能先后进入锁内。

Python 的标准 `threading.Lock` 没有一个可以直接照搬 Java `volatile` 的关键词。没有测量到瓶颈时，完整加锁比自行设计锁外快速路径更容易判断正确性。

书中用较大的倍数形容同步开销，不能当作你当前系统的性能结论。是否需要优化，应依据实际运行环境与测量。

## 5. 完整 Python 示例：同一实例，安全累计批次数

同目录 [示例.py](示例.py)，运行 `python 示例.py`，要求 Python 3.10+。

示例把锅炉管理中的“累计完成批次”抽出来，专门展示两把锁的不同职责。它不连接设备，也不模拟真实生产安全控制。

```python
from concurrent.futures import ThreadPoolExecutor
from threading import Lock


class BatchCounter:
    _instance = None
    _creation_lock = Lock()

    def __new__(cls):
        # ponytail: 每次构造都加锁；有性能证据时优先在入口创建后传递实例。
        with cls._creation_lock:
            if cls._instance is None:
                instance = super().__new__(cls)
                instance._value = 0
                instance._state_lock = Lock()
                cls._instance = instance
            return cls._instance

    def __init_subclass__(cls, **kwargs):
        raise TypeError("本教学单例不支持继承")

    def finish_batch(self) -> int:
        with self._state_lock:
            self._value += 1
            return self._value

    def value(self) -> int:
        with self._state_lock:
            return self._value


def demo() -> None:
    shared = BatchCounter()
    before = shared.value()

    def work(_: int) -> tuple[bool, int]:
        counter = BatchCounter()
        return counter is shared, counter.finish_batch()

    with ThreadPoolExecutor(max_workers=8) as pool:
        results = list(pool.map(work, range(100)))

    same_instance = all(same for same, _ in results)
    numbers = sorted(number for _, number in results)
    if not same_instance or numbers != list(range(before + 1, before + 101)):
        raise AssertionError("实例唯一性或累计操作不正确")
    if BatchCounter().value() != before + 100:
        raise AssertionError("重复构造不应重置状态")
    print(f"所有线程拿到同一实例：{same_instance}")
    print(f"本轮累计完成批次：{shared.value() - before}")
    print("自检通过")


if __name__ == "__main__":
    demo()
```

预期输出：

```text
所有线程拿到同一实例：True
本轮累计完成批次：100
自检通过
```

`__new__` 负责返回实例。本例只在创建新实例时初始化字段；没有把 `_value = 0` 写入 `__init__`，因为正常构造语法即使拿回旧实例，仍可能再次调用 `__init__`，导致状态被重置。

示例禁止继承，避免子类误复用基类单例字段。它只覆盖同一进程、同一类对象的正常构造调用，不承诺阻止绕过构造、重载模块、复制或序列化等路径。Python 下划线属性也不是真正的私有访问控制。

## 6. 最容易漏掉的一点：实例安全，不等于状态安全

`_creation_lock` 保护“是否已有实例 → 创建 → 保存”的过程。

`_state_lock` 保护共享计数器的读取和修改。**确保只有一个对象，恰恰意味着更多调用者会同时访问同一份状态。**

所以正确的单例获取方式，并不能自动让 `count += 1` 或“先检查再执行”这类业务操作安全。

回到锅炉：即使 `fill()`、`boil()`、`drain()` 各自加锁，整个三步流程仍可能与另一个线程交错。若要求一批次不可被其他批次插入，就要把完整批次的操作范围纳入同步或明确的状态协调。真实设备还要有设备层约束，单例类不能代替它。

并发自检能发现实现退化，但不能穷尽所有调度；正确性首先来自明确的加锁范围与共享状态边界。

## 7. 实际项目里，先决定是否真的需要它

如果你的需求只是“多个对象共享同一个服务”，可以在入口创建一次，然后通过构造参数传给使用者。这样测试时更容易替换，也更容易看见依赖。

如果你的需求是“同一进程的正常调用不能创建第二个实例”，再考虑类级单例。还要确定它何时释放资源、不同测试是否互相污染、能否容忍全局状态。

如果你的需求是“整个集群只有一个任务执行者”或“跨进程编号唯一”，单例类不够。不同进程各有独立内存，需要在共享存储或协调机制上设计唯一性。这不是多加一把 Python 线程锁就能解决的问题。

| 常见误解 | 正确判断 |
| --- | --- |
| 名字叫 singleton 就保证唯一 | 看构造路径、并发与作用范围 |
| 单例保证每次业务操作线程安全 | 实例创建和业务状态要分别处理 |
| 所有方法做成静态方法就是单例 | 静态工具方法不一定需要对象；它们与共享对象的职责不同 |
| 到处获取单例，比传参方便就更好 | 全局依赖更隐蔽，测试隔离与替换更困难 |
| Java 枚举解决了跨进程或跨类加载器唯一性 | 没有；唯一性仍受运行环境和类型身份范围限制 |

## 8. 三分钟练习：识别两个不同的 bug

题目 A：开发者在单例类的 `__init__` 中写 `self._value = 0`，每次 `BatchCounter()` 后计数归零，原因是什么？

题目 B：实例创建已经加锁，但 `finish_batch()` 不再加锁，能否保证累计正确？

<details>
<summary>查看参考答案与改法</summary>

A：`__new__` 复用旧实例，不代表 `__init__` 只执行一次。应在受保护的首次创建阶段初始化状态，或用明确且同步的初始化机制，不能每次重置。

B：不能从实例唯一推导共享数据操作安全。恢复围绕整个更新操作的锁；只保护读取、把加一和写回放在锁外，也不够。

动手任务：把 demo 中任务数从 100 改为 200，并同步更新自检期望值。输出应为 200，所有任务仍拿到同一实例。不要因为一次偶然通过就删除业务锁。

</details>

<details>
<summary>自测：启动两个 Python 进程，它们的 BatchCounter 是同一个吗？</summary>

不是。两个进程各有类、静态字段和堆内存，因此各有自己的实例。线程池示例只验证一个进程里的共享。

</details>

## 9. 五章串起来：看到需求，先认变化点

| 你要解决的问题 | 优先想到 | 一句话辨别 |
| --- | --- | --- |
| 同一任务换一种做法 | 策略 | 把行为传进去，可替换 |
| 一次变化通知多个对象 | 观察者 | 订阅、退订、通知 |
| 给一个对象叠加可选功能 | 装饰者 | 同接口包装并委托 |
| 创建选择与使用流程分开 | 工厂 | 集中创建 / 子类创建 / 创建产品家族 |
| 在明确范围内限制实例数量 | 单件 | 控制实例创建，并单独管理共享状态 |

综合练习：订单按配送方式选运费算法，是策略；订单状态更新通知多个页面，是观察者；日志与计时层包装同接口服务，可以是装饰者；切换一套配套供应商产品，是抽象工厂。共享一个服务实例可以直接在入口组装，不一定要额外使用单件模式。
