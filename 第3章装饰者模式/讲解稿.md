# 第3章｜装饰者模式：一层一层加功能

[章节测验](练习题.html) · [Markdown 题稿](练习题.md)

> 学习目标：不修改基础对象，把可选功能按需叠加；能顺着包装链解释调用和返回，并区分装饰者模式与 Python 的 @ 语法。

建议用时：速读 8 分钟，运行与练习 10 分钟。抓住“同一接口、持有对象、委托后增强”这三个动作。

## 1. 先记住这一句话

**装饰者模式：用具有相同使用接口的新对象，包住原对象，在委托调用的前后增加功能。**

一杯浓缩咖啡，加一份摩卡，再加奶泡，还是可以用“饮料”的方式询问描述和价格。每层只处理自己增加的部分，其余交给里面那层。

策略是换一种做法，装饰者是把功能叠上去。

## 2. 书里的咖啡店，为什么需要包装

如果每种组合都有一个类，很快就会出现“咖啡加摩卡”“咖啡加双份摩卡加奶泡”等大量类。调料价格变一次，很多组合都可能要修改。

改成在父类里保存 `has_milk`、`has_mocha` 等布尔字段也有局限：增加调料要改父类；布尔字段不能自然表达双份；不适合某种饮料的调料也被塞进共同父类。

包装把组合从“写死在类名中”移到“创建对象时决定”：`Whip(Mocha(Mocha(Espresso())))`。基础饮料与每种配料各负责自己的价格，组合时再计算总价。

**开放—关闭原则：对某类扩展开放，让已有稳定逻辑尽量不用修改。** 这里对“新增一种包装功能”开放，不代表永远不能修代码，更不代表所有未来需求都能免修改。

## 3. 三个角色与一条调用链

| 角色 | 本例 | 责任 |
| --- | --- | --- |
| 组件接口 | Beverage | 约定 description 与 cost |
| 具体组件 | Espresso | 提供基础饮料和基础价格 |
| 装饰者 | Mocha、Whip | 保存一个 Beverage，委托并加上自己的功能 |

调用方向：`Whip → Mocha → Mocha → Espresso`。

返回方向：`1800 → 2100 → 2400 → 2600 分`。

价格是本讲解自定的示例数据。用整数“分”避免二进制浮点数计算金额的误差，不需要为了本例引入货币库。

## 4. 完整 Python 示例：双份摩卡加奶泡

同目录 [示例.py](示例.py)，使用 Python 3.10+ 执行 `python 示例.py`。

```python
from dataclasses import dataclass
from typing import Protocol


class Beverage(Protocol):
    def description(self) -> str: ...
    def cost(self) -> int: ...  # 金额单位：分。


class Espresso:
    def description(self) -> str:
        return "浓缩咖啡"

    def cost(self) -> int:
        return 1800


@dataclass(frozen=True)
class Mocha:
    beverage: Beverage

    def description(self) -> str:
        return self.beverage.description() + " + 摩卡"

    def cost(self) -> int:
        return self.beverage.cost() + 300


@dataclass(frozen=True)
class Whip:
    beverage: Beverage

    def description(self) -> str:
        return self.beverage.description() + " + 奶泡"

    def cost(self) -> int:
        return self.beverage.cost() + 200


def demo() -> None:
    base = Espresso()
    drink: Beverage = Whip(Mocha(Mocha(base)))
    expected_name = "浓缩咖啡 + 摩卡 + 摩卡 + 奶泡"
    if drink.cost() != 2600 or drink.description() != expected_name:
        raise AssertionError("包装链计算错误")
    if base.cost() != 1800:
        raise AssertionError("包装不应修改基础饮料")
    print(drink.description())
    print(f"价格：{drink.cost() / 100:.2f} 元")
    print("自检通过")


if __name__ == "__main__":
    demo()
```

预期输出：

```text
浓缩咖啡 + 摩卡 + 摩卡 + 奶泡
价格：26.00 元
自检通过
```

`Protocol` 说明对象应提供什么方法，供读者和类型检查器理解；它不会自动在运行时校验对象。`Espresso` 和两种装饰者不必显式继承它，只要满足约定即可。

书中用一个抽象装饰者类共享类型关系；这个短小 Python 版本省去中间层，用统一的结构化接口保留同样的包装关系。

## 5. 一次 cost 调用发生了什么

1. 客户只调用最外层 `drink.cost()`，也就是奶泡层。
2. 奶泡层先调用里面的摩卡，摩卡再调用里面的摩卡，直到基础咖啡。
3. 基础咖啡返回 1800；每层在返回值上加自己的价格。
4. 调用者拿到 2600，不必理解内部包了几层。

**必须保留并使用最外层引用。** 如果后来还拿 `base.cost()` 结账，当然只会收到 18 元，因为你绕开了所有包装。

本例只做固定加法，调换摩卡和奶泡不改变总价，但会改变描述顺序。若一层打九折、一层加固定配送费，包装顺序会影响金额：`(原价 + 配送费) × 0.9` 与 `原价 × 0.9 + 配送费` 不同。

## 6. Python 的 @decorator 与这个模式有什么关系

Python 的 `@decorate` 是语法：函数定义后，把函数交给 `decorate`，用返回值替换原名字。它可以用于包装，也能用于注册、标记等其他用途。

装饰者模式则是设计关系：**维持共同接口、持有被包装对象、通过委托扩展行为。** 所以不是每个 `@` 都是装饰者模式；装饰者模式也完全不需要 `@`。

一个包裹函数的计时器可能体现同样的思想。实际写函数包装时，常用 `functools.wraps` 保留原函数的名称、文档等信息；普通元数据装饰并不能单凭 `@` 就算本模式。

书中的 Java I/O 是另一种应用：基础输入流负责读取，缓冲层等包装提供附加能力。Python 中遇到 I/O，先使用 `open()`、`io`、`gzip` 等已有能力，不要为了练模式重新实现文件系统。

## 7. 如何扩展，以及哪些地方会变难

新增焦糖：写一个同接口包装类，价格返回内部价格加焦糖价，再在下单入口包一层。基础咖啡和已有摩卡不变。

新增杯型：明确杯型归谁管理。一个常见做法是基础饮料保存杯型，包装层的 `size` 访问统一转交内部对象，配料按它计费。不要每层各存一份默认杯型，否则可能出现大杯咖啡按小杯配料结账。若允许改杯型，还要定义修改从哪层向内传递。

| 适合用 | 需要另想办法 |
| --- | --- |
| 功能可选、可组合、可以多层叠加 | 特性之间大量互斥、强依赖，需要跨层检查 |
| 客户能只依赖共同接口 | 客户到处检查具体类或强制拆开包装 |
| 在调用前后添加独立能力 | 只是几项数据加总，用列表求和就够了 |

包装层多会让调试路径变长；对象创建也更复杂。装饰者不负责自动禁止非法组合，订单约束需要在组装入口验证。抽象的收益应当超过这份复杂度。

## 8. 三分钟练习：新增焦糖，基础类不动

任务：焦糖加收 400 分，组合一杯“浓缩咖啡 + 焦糖 + 奶泡”，预期 2400 分。不要修改 `Espresso`、`Mocha`、`Whip`。

<details>
<summary>查看参考答案</summary>

```python
@dataclass(frozen=True)
class Caramel:
    beverage: Beverage

    def description(self) -> str:
        return self.beverage.description() + " + 焦糖"

    def cost(self) -> int:
        return self.beverage.cost() + 400

drink = Whip(Caramel(Espresso()))
assert drink.cost() == 2400
```

检查点：新行为在新类里；创建对象的代码可以改变，这不违背开放—关闭原则。不要把“修改入口组装”误认为“修改基础算法”。

</details>

<details>
<summary>自测：包装后，为什么 isinstance(drink, Espresso) 不再可靠？</summary>

外层对象可能是 Whip 或 Mocha，它仍满足 Beverage 约定，但不再是 Espresso 实例。客户应通过共同接口工作。若业务确实需要咖啡种类，应把它作为接口中的明确数据，而不是强拆包装链。

</details>
