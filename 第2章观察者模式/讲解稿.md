# 第2章｜观察者模式：一处变化，多处自动响应

[章节测验](练习题.html) · [Markdown 题稿](练习题.md)

> 学习目标：把“数据变了就逐个调用具体页面”的代码，改成可订阅、可退订的通知机制，并说清它的同步、顺序和异常边界。

建议用时：速读 8 分钟，运行与练习 12 分钟。先读第 1、3、5、7 节，再运行气象站。

## 1. 先记住这一句话

**观察者模式：一个对象维护订阅关系，状态变化后，通知所有已订阅的对象。**

像订阅天气提醒：气象站产生新数据，你决定订阅或退订；气象站不必知道你收到数据后是更新屏幕、记录历史，还是发出提示。

它描述一对多的依赖关系。一个观察者也可以订阅多个主题；同一个对象甚至可以既接收上游通知，又通知下游。

## 2. 书中的气象站，真正难在哪里

第一版直接写：更新当前天气显示 → 更新统计显示 → 更新预报显示。这能运行，但气象站知道所有具体显示类，新增一个显示就要改它。

变化的是“哪些对象关心数据，以及收到数据后做什么”；相对稳定的是“获得新测量值后发送通知”。把订阅名单独立管理，气象站只调用统一约定，显示就能自由增减。

| 角色 | 书中对象 | Python 示例 |
| --- | --- | --- |
| 主题 Subject | WeatherData | WeatherStation，保存状态与订阅者 |
| 观察者 Observer | 各个显示组件 | 接收 Weather 参数的回调函数 |
| 注册 / 移除 | 加入或离开通知列表 | subscribe / unsubscribe |
| 通知 | notifyObservers | publish 中遍历回调 |

核心原则是松耦合：双方需要知道交互约定，但主题不依赖某个具体显示的实现。松耦合不是零依赖。

## 3. 推与拉：通知之后，数据怎么给

| 方式 | 调用形式 | 好处 | 代价 |
| --- | --- | --- | --- |
| 推 | `callback(weather)` | 一次拿到这次事件的数据；快照可被多个观察者读取 | 数据约定变化可能影响消费者 |
| 拉 | `callback()`，观察者再读主题 | 观察者按需读取；新增 getter 不必改全部回调签名 | 观察者依赖读取接口；并发时多次读取可能不是同一版本 |

书中先推送温度、湿度、气压，再改成接到通知后拉取。本例选择推送一个不可变的 `Weather` 快照，让事件数据与某一次发布绑定。**没有哪种方式永远更好。**

推和拉都不等于异步：调用回调时直接执行其代码，就是同步通知。要跨线程或跨进程，还需要额外的调度或通信机制。

## 4. 完整 Python 示例：两个订阅者与一次退订

同目录 [示例.py](示例.py) 可直接运行：`python 示例.py`。要求 Python 3.10+，只用标准库。

```python
from dataclasses import dataclass
from math import isfinite
from typing import Callable


@dataclass(frozen=True)
class Weather:
    temperature: float
    humidity: float


Observer = Callable[[Weather], None]


class WeatherStation:
    def __init__(self) -> None:
        self.latest: Weather | None = None
        self._observers: list[Observer] = []

    def subscribe(self, observer: Observer) -> None:
        if not callable(observer):
            raise TypeError("观察者必须可调用")
        if observer not in self._observers:
            self._observers.append(observer)

    def unsubscribe(self, observer: Observer) -> None:
        if observer in self._observers:
            self._observers.remove(observer)

    def publish(self, temperature: float, humidity: float) -> None:
        if not isfinite(temperature) or not isfinite(humidity):
            raise ValueError("测量值必须是有限数")
        if not 0 <= humidity <= 100:
            raise ValueError("湿度必须在 0 到 100 之间")
        event = Weather(temperature, humidity)
        self.latest = event
        # ponytail: 单线程同步通知；需要并发发布时再设计队列与调度。
        for observer in tuple(self._observers):
            observer(event)


def demo() -> None:
    station = WeatherStation()
    screen: list[Weather] = []
    history: list[Weather] = []

    def show(weather: Weather) -> None:
        screen.append(weather)
        print(f"屏幕：{weather.temperature:.0f}°C / {weather.humidity:.0f}%")

    station.subscribe(show)
    station.subscribe(history.append)
    station.subscribe(show)  # 重复订阅不会重复通知。
    station.publish(25, 60)
    station.unsubscribe(show)
    station.publish(28, 65)

    if len(screen) != 1 or history != [Weather(25, 60), Weather(28, 65)]:
        raise AssertionError("订阅或退订行为不正确")
    try:
        station.publish(20, 101)
    except ValueError:
        pass
    else:
        raise AssertionError("必须拒绝非法湿度")
    if station.latest != Weather(28, 65):
        raise AssertionError("非法数据不应覆盖有效状态")
    print(f"历史记录：{len(history)} 条")
    print("自检通过")


if __name__ == "__main__":
    demo()
```

预期输出：

```text
屏幕：25°C / 60%
历史记录：2 条
自检通过
```

## 5. 一次 publish 到底发生了什么

1. 先校验新数据，失败时不改变当前状态。
2. 创建不可变快照，保存为 `latest`。
3. 拷贝当前订阅列表，再依次执行其中的回调。
4. 第一次发布时，屏幕和历史各收到一份；退订屏幕后，第二次只进入历史。

`tuple(self._observers)` 解决的是“回调执行中修改列表”的遍历问题。本例约定：本轮按开始时的名单通知，新订阅从下一轮生效；本轮中途退订的回调仍可能收到本轮消息。**列表快照不等于线程安全。**

`frozen=True` 在这里足够，因为事件只有数值字段；如果将来放入可变列表，冻结 dataclass 并不会自动把内部列表也冻结。

本例观察者抛异常会中断发布，状态已经更新，后面的回调可能没执行。这是明确的失败语义。若业务要求所有订阅者都尝试执行，应逐个捕获并记录异常，最后汇总或上报，不能直接吞掉错误。

## 6. 工作中怎么用，以及什么时候不用

适合：界面数据更新多个视图、编辑器事件通知、进程内状态变化触发多个独立响应。新增消费者只需写回调并注册，不必修改主题的发布逻辑。

例如增加温度超标提示：实现接收 `Weather` 的函数，只在温度超过阈值时输出提示，然后订阅它。这里阈值应是业务配置，不能从设计模式里推导出来。

不适合：步骤必须严格排序、失败必须整体回滚的主业务流程。比如“扣库存成功才扣款”，通常应明确编排，而不是让两个互不知情的观察者自行协调。

**观察者与消息队列不是一回事。** 本例是同一进程内直接调用；跨进程发布订阅还涉及持久化、重试、重复消费和顺序等问题，不能只复制这段代码就获得那些能力。

Python 函数、绑定方法都能做观察者，已有事件框架时优先复用。书中还用 Swing 按钮监听说明同一思想；旧 Java `Observable/Observer` API 已被弃用这一点不影响模式本身的价值。

## 7. 四个必须记住的边界

| 问题 | 本例行为 | 在项目里要作出的决定 |
| --- | --- | --- |
| 慢回调 | 阻塞本次发布 | 是否允许同步等待，是否需要后台队列 |
| 回调异常 | 立即传播，中止后续通知 | 中止、继续并汇总，还是重试 |
| 订阅者生命周期 | 主题持有强引用 | 页面关闭或对象停用时退订，避免长期残留 |
| 通知顺序 | 当前列表按注册顺序遍历 | 若业务依赖顺序，要把它写成明确约定，不能假设所有实现都一样 |

回调里再次发布还可能造成递归通知或循环。没有这种需求时，不要在回调中修改同一主题；有需求时先定义事件顺序，再考虑队列。

## 8. 三分钟练习：增加高温提示

任务：温度达到 30°C 时输出提示，29°C 时不提示；订阅后发布两次，再退订。不要修改 `publish()`。

<details>
<summary>查看参考答案</summary>

```python
alerts = []

def warn(weather: Weather) -> None:
    if weather.temperature >= 30:
        alerts.append(weather.temperature)

station = WeatherStation()
station.subscribe(warn)
station.publish(29, 50)
station.publish(31, 50)
station.unsubscribe(warn)
station.publish(35, 50)
assert alerts == [31]
```

检查点：只改变消费者与订阅关系，气象站核心逻辑不变。若只订阅一次却收到两次通知，检查是否重复注册、重复发布或产生递归通知。

</details>

<details>
<summary>自测：推送一个对象，就一定比拉取好吗？</summary>

不是。推送快照有利于表达某次事件；拉取适合消费者只需要不同的小部分状态。判断依据是数据一致性、接口变化频率和调用成本，不是名字。

</details>
